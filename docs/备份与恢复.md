# 备份与恢复

Supabase 免费版**没有每日备份**。整个球群的比分、聊天、语音、账号
全在那一个项目里，而它现在没有任何一份副本 —— 这是这个 App 唯一
一件「数据可能真的没了」的风险，别的问题最多是不好用。

这份手册是照着做一遍的流程，不是建议。**没试过的备份等于没有备份**，
所以下面第三步（真的恢复一次）不能跳。

> **2026-09-16 第一次真跑过了。** 结论：救得回来，一行没丢。
> 这一版手册是照着那次实跑重写的 —— 原来那一版有四处和现在的
> Supabase 后台对不上，还漏了一件挺严重的事（见「备份文件有多敏感」）。
> 每一条的来历都写在下面的演练记录里。

---

## 备份什么

三样，缺一样都救不回一个完整的 App：

| 东西 | 在哪 | 丢了会怎样 |
|---|---|---|
| `public` 里的业务表 | Postgres `public` | 比分、排名、聊天、举报、反馈全没 |
| 账号 | Postgres `auth.users` | 表还在，但每一行都指向不存在的人，谁都登录不了 |
| 语音文件 | Storage 的 `voice` 桶 | 聊天记录里的语音气泡全变成点不开的 |

**别在这儿硬写一张表清单。** 原来这里列了 9 张，实跑时数出来是 11 张
（后来加的 `errors` 和 `leaderboard` 没人记得回来补）。清单一定会过时，
而过时的清单比没有清单更坏 —— 它会让人以为自己检查过了。

要看当时到底有几张，导完之后问 dump 本身：

```bash
pg_restore -l rally-public-$STAMP.dump | grep "TABLE DATA"
```

## ⚠️ 先说三件不能做错的事

**1. 备份文件里有所有人的私聊。** 它不是代码，永远不要提交进这个仓库，
也别丢进任何会同步到公开地方的文件夹。仓库的 `.gitignore` 已经挡了
`backups/` 和 `*.dump`，但那是最后一道，不是第一道。导完顺手
`chmod 600`。

**2. 连接串里有数据库密码。** 只在你自己的电脑上用 —— 不要贴进聊天
窗口、不要截图、不要写进任何文件后提交。**实跑那次这一条被违反了两次**，
两次都是「以为屏幕上看不见」。下面第一步里那套做法（让 psql 自己问密码）
就是为了让它不可能发生。

**3. 每次贴终端截图之前先 `clear`。** 连接串和密码一旦出现在屏幕上，
截图就带出去了。

## 一、把数据库导出来

### 装工具（macOS）

Mac 不自带 `pg_dump`。

```bash
brew install libpq
echo "export PATH=\"$(brew --prefix libpq)/bin:\$PATH\"" >> ~/.zshrc
source ~/.zshrc
pg_dump --version
```

`libpq` 是 keg-only 的，Homebrew 故意不挂 PATH，所以中间那句不能省。

**版本规矩：本机的 `pg_dump` 不能低于服务器。** 装最新的就永远安全，
不用先去查服务器是哪一版。（实跑：客户端 18.6，服务器 17.6，没问题。）

### 拿连接串

**`Project Settings → Database` 这条路已经没有了。** 现在在页面顶上那个
**`⊸ Connect`** 按钮里：

`⊸ Connect` → **Direct Connection**（那个圆柱图标的方块）→ 里面选
**Connection Method**：

| 选项 | 端口 | 用不用 |
|---|---|---|
| Direct connection | 5432 | ❌ 只有 IPv6，家宽和手机热点连不上 |
| **Session pooler** | **5432** | ✅ **用这个**，IPv4 |
| Transaction pooler | 6543 | ❌ `pg_dump` 在它上面跑不起来 |

Type 选 **URI**。

**忘了数据库密码**：重设页面还在，只是侧边栏不链过去了，直接开
`https://supabase.com/dashboard/project/<项目ref>/settings/database`，
找 Reset database password。**重设不影响 App** —— App 走的是
`sb_publishable_…`，和数据库密码是两回事。

重设时用 **Generate a password**，别自己想一个：自己想的容易在几个地方
重复用，露一次就全露了。生成完先存进密码管理器。

### 连上（这套做法是为了让密码不经过 shell）

把连接串里的 `:[YOUR-PASSWORD]` **整段删掉**，只留下：

```bash
PGURL="postgresql://postgres.<项目ref>@aws-0-<区域>.pooler.supabase.com:5432/postgres"
```

（一次只粘一行。把好几行一起粘进终端，前一行的 `read` 会把后一行
当成输入吃掉 —— 实跑时踩过。）

然后：

```bash
psql "$PGURL" -c "select version();"
```

它会自己弹 `Password for user ...:`，在那儿粘密码。**这条路比把密码塞进
变量或写进连接串都干净**：密码由 libpq 自己收，不进命令行、不进
history、不显示在屏幕上。后面的 `pg_dump` / `pg_restore` 也一样会问。

**连不上时先看这个**：

```bash
echo "[${PGURL:0:25}]"
```

该是 `[postgresql://postgres.xxx]`。实跑时开头多打了一个字母
（`ppostgresql://`），psql 就**不把它当连接串，改当数据库名**，
于是去连本机，报的是

```
connection to server on socket "/tmp/.s.PGSQL.5432" failed
```

—— 这句话跟「开头拼错了」看起来毫无关系，不知道的话能查很久。

### 导

```bash
mkdir -p ~/rally-backups && cd ~/rally-backups
STAMP=$(date +%Y%m%d)

pg_dump "$PGURL" --schema=public --no-owner --no-privileges \
  -Fc -f rally-public-$STAMP.dump

pg_dump "$PGURL" --schema=auth --no-owner --no-privileges \
  -Fc -f rally-auth-$STAMP.dump

chmod 600 rally-*.dump
```

`~/rally-backups` 不在 iCloud 同步的「桌面与文稿」里，特意选的。

**成功的时候这两句什么都不打印** —— 别以为卡住了。

### 确认不是空壳

文件有大小 ≠ 里面有数据。`-Fc` 是压缩格式，一个只有表结构、
没有一行数据的 dump 也能有几十 K。

```bash
pg_restore -l rally-public-$STAMP.dump | grep "TABLE DATA"
pg_restore -l rally-auth-$STAMP.dump  | grep "TABLE DATA"
```

`public` 那份该列出当时所有的业务表，`auth` 那份里要看得到 `users`。

### 记下这一刻的数

**这一步要在导出之后立刻做，而且数字要记下来。** 恢复之后要拿它对。

```sql
select 'records' as 表, count(*) as 行数 from public.records
union all select 'club_members', count(*) from public.club_members
union all select 'messages', count(*) from public.messages
union all select 'zz1_auth_users', count(*) from auth.users
union all select 'zz2_有主人的球员', count(*)
  from public.records r
  join auth.users u on u.id::text = r.data->>'ownerId'
  where r.kind = 'player' and r.deleted = false
order by 1;
```

（其余的表照着 `pg_restore -l` 数出来的清单补。）

## 二、把语音文件导出来

语音不在数据库里，在 Storage 的 `voice` 桶。数据库的 dump **不含**它们。

Supabase CLI 装好之后（`npm i -g supabase`，然后 `supabase login`）：

```bash
supabase storage cp -r ss://voice ./voice-$STAMP --experimental
```

> `storage` 这组命令还标着 experimental，不同版本参数可能不一样。
> 跑之前先 `supabase storage --help` 看一眼当前版本怎么写。
> 实在不行就在后台 Storage 页面手动下载 —— 现在文件不多。
>
> **这一段还没实跑过。** 2026-09-16 那次只验了数据库那两份。

## 三、恢复演练（**这一步是重点，别跳**）

前两步只是产出了两个文件。**文件能不能用，只有真的恢复一次才知道。**

### 先确认有位子

免费版**一个组织只能有 2 个项目**。已经有两个的话，这一步直接走不下去
—— 后台会拦住你，写着 `Limit: 2 free projects`。

先去 https://supabase.com/dashboard/projects **Pause** 掉一个不用的
（Pause 是可逆的，别删），腾出位子。演练完再恢复回去。

### 建一个空项目

New project：

- 名字 `rally-restore-test`（跑完就删）
- 区域随便 —— 是个靶子，两个 dump 加起来两百来 KB，传哪儿都一样快
- 密码让它生成，**先存进密码管理器**

建完等一两分钟。然后照上面同一套路子拿它的连接串（`Connect` →
Session pooler → URI，去掉密码那段），存成 `NEWURL`。

### 恢复

**顺序不能反**：业务表的外键指向 `auth.users`，反过来会一路报外键错。

```bash
pg_restore --no-owner --no-privileges -d "$NEWURL" \
  rally-auth-$STAMP.dump 2>&1 | tee restore-auth.log

pg_restore --no-owner --no-privileges -d "$NEWURL" \
  rally-public-$STAMP.dump 2>&1 | tee restore-public.log
```

### ⚠️ `auth` 那一份会刷两百多条错，那是正常的

实跑：**228 条 `errors ignored on restore`**，几乎全是

```
ERROR: must be owner of table users
Command was: ALTER TABLE auth.users ENABLE ROW LEVEL SECURITY;
```

原因：`auth` 那些表归 `supabase_auth_admin` 所有，你用 `postgres` 身份
改不动它们的设置。**但新项目里这些表本来就已经建好、RLS 也已经开好了**，
所以这些改动本来就不需要做。

**这一段必须提前说。** 不说的话，看到两百多条红字的人会以为恢复失败了，
而实际上数据一行不少 —— 下面那一句就是证据：

```bash
psql "$NEWURL" -c "select count(*) from auth.users;"
```

`public` 那一份的错会少得多（实跑只有 2 条，都无害）。

### ⚠️ 备份文件有多敏感：它里面可能有一把万能钥匙

实跑那次，`public` 的恢复日志里打出了这么一行：

```
CREATE TRIGGER "notify-on-new-session" AFTER INSERT ON public.records
  ... 'Authorization":"Bearer eyJhbGciOi...'
```

那个 Bearer 解开是 `{"role":"service_role"}` —— **绕过所有 RLS 的
万能钥匙**，被数据库 Webhook 写死在触发器定义里，于是**每一份 dump
都带着它**。谁拿到备份文件，就等于拿到整个数据库。

那个触发器已经删掉了（见 `supabase/019-drop-session-webhook.sql`），
所以现在的备份里没有它。但这条规矩要留着：

> **恢复日志里如果出现 `Bearer`，说明数据库里又有东西把密钥写死进了
> 定义。** 立刻查清楚是什么，并且把那份日志和 dump 当成密钥文件对待。

顺手：看完日志就删掉它们。

```bash
rm restore-auth.log restore-public.log
```

### 验：数得对不对

在**新项目**里跑第一步里那同一句 count 查询。

**拿它和「导出那一刻记下的数」比，不是和「现在的原项目」比。**
原来这里写的是「同一句在原项目里也跑一遍，两边数字要一样」——
那句话是错的：源库一直在被人用，你演练的这一两个小时里它会往前走。

实跑就撞上了：`records` 原项目 296、恢复出来 289，差 7。查下来那 7 行
全是演练期间为了测推送开的局：

```sql
-- 拿恢复出来那份里最新一行的时间去问原项目
select kind, id, deleted, updated_at
from public.records
where updated_at > '<恢复出来那份的最新 updated_at>'
order by updated_at;
```

七行、全是那段时间的 session —— 对上了，说明**一行没丢**。

### 再验一件事：比分还认得出人吗

数字对得上还不够，外键有没有接上也要看 —— 就是 count 查询里
`zz2_有主人的球员` 那一行。

它该和原项目一致（实跑 17 == 17）。是 0 的话说明 `auth.users`
没恢复成功，数据虽然在，但没人登录得进去。

### 收尾

演练完**把测试项目删掉** —— 它里面是一份完整的私聊副本，
留着就是多一个会漏的地方。然后把之前 Pause 的那个项目恢复回来。

## 多久做一次

现在这个量级（一个球群、十几个人），**一个月一次**够了。
开放给别的球群之后改成每两周。

真嫌麻烦的话，$25/月 的 Supabase Pro 自带每日备份和 7 天 PITR ——
那笔钱买的就是不用做这件事。但**就算买了 Pro，也要做一次恢复演练**，
理由一样：没试过的备份等于没有备份。

## 演练记录

做一次填一行。空着的话，就说明这份手册还没被验证过。

| 日期 | 导出大小 | 恢复后数字对得上吗 | 遇到什么问题 |
|---|---|---|---|
| 2026-09-16 | public 79 KB / auth 116 KB | ✅ 全对（records 289=289，auth.users 17=17，有主人的球员 17=17） | 见下面七条 |

**2026-09-16 第一次实跑，抓到七件事**（这一版手册已经全部改进去了）：

1. **后台路径变了。** `Project Settings → Database` 没有了，连接串挪到
   顶上的 `⊸ Connect` 按钮里。重设密码那一页还在，只是侧边栏不链了。
2. **必须挑 Session pooler。** Direct 只有 IPv6 连不上，Transaction
   pooler（6543）`pg_dump` 跑不起来。
3. **表清单过时了。** 手册写 9 张，实际 11 张（`errors`、`leaderboard`
   是后来加的）。所以改成「用 `pg_restore -l` 去数」，不再硬写清单。
4. **免费版只能有 2 个项目。** 已经满了的话演练直接开不了头，得先
   Pause 一个。手册原来完全没提。
5. **`auth` 恢复会刷 228 条 `must be owner` 的错**，而数据其实一行不少。
   原来手册只说「报一些警告是正常的」，太轻描淡写。
6. **dump 里有一把 service_role 钥匙**（webhook 触发器把它写死在定义
   里）。这是这次最值钱的发现 —— 一个一直存在的设计缺陷，跟备份没
   关系，只是备份把它照出来了。触发器已删。
7. **对数要比「导出那一刻」的数。** 源库在演练期间还在被使用，
   拿「现在」的数去比，会看到差几行，照做的人会以为备份坏了。

另外两件不算发现、但下次一定会再遇到的：**Mac 要自己装 `pg_dump`**，
以及**连接串开头多一个字母时，psql 会去连本地而不是报格式错**。
都写进上面了。
